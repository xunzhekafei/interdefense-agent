# 项目计划书（草稿）

> 基于官方模板结构的 Markdown 草稿，提交前转成 `.docx` 并补封面/版本号。
> **提交版不得出现学校、学生姓名、指导教师**；队名用约定的代号。

## 1 项目概述

### 1.1 项目背景

大学生在毕业答辩、课程汇报前普遍缺少「被追问」的练习机会：一次汇报只讲一遍，讲完没有人提问，
论证里的空洞（没有基线、样本量、口径、个人贡献边界）往往到正式场合才暴露。现有工具大致分两类：
题库式模拟面试按岗位泛问，和讲稿无关；演讲/表达类工具只给语速、口头禅等表层反馈，不触碰论证。
两类都无法回答学生最关心的问题——**「我这份讲稿，评委最可能从哪一句开始问？」**

### 1.2 项目内容

本作品把「生成式 AI 的追问能力」锚定到学生自己的讲稿上，形成可检查、可修正的练习闭环：

1. **陈述单元切分**：讲稿按标题/空行/句子切成 `U1…Un`，每段保留在原文中的位置。
2. **摘要卡确认**：AI 先概括每段真正的主张、指出缺证据的地方；学生逐条确认、改写或驳回。
   理解错了，追问越准越偏，所以先确认再开始。
3. **锚定单元追问**：评委式提问针对具体单元（「你结果部分说准确率 81%，基线是多少？」），
   一次一题、同一单元最多追问两层。
4. **答辩复盘报告**：逐题评分并回链到讲稿原句；四个维度为方法与论证严谨性、工作量与完整性、
   创新与个人贡献、表达与应答；证据必须是学生回答的逐字原文。
5. **下一场检验**：确认过的短板变成下一场的定向检验点，报告如实说明哪些点仍未被问到。

场景覆盖毕业答辩与课程汇报，求职面试作为能力底座保留；移动端可安装到手机桌面，
用系统语音识别作答。

### 1.3 创新点

#### 1.3.1 技术创新点

- **陈述单元锚定**：把追问从「针对上一句话」变成「针对讲稿的某一段」，报告里的每条评价都能
  回到原文位置。模型漏标注单元时，用问题与单元的最长公共片段确定性补回链（宁漏不错）。
- **证据逐字校验**：评分给出的证据必须能在学生回答中找到连续原文，改写或概括会触发重试，
  重试耗尽则标记未通过——把「有依据的反馈」变成机器可验证的约束。
- **评分口径代码化**：维度、权重、分档标尺、场景差异集中在单一模块；维度均分与总分由代码
  从逐题分计算，模型只负责判断，不负责算数，避免同一份报告出现两个总分。

#### 1.3.2 功能创新点

- **摘要卡可修正**：学生先纠正 AI 对讲稿的理解，确认结果再进入追问，并成为下一场的检验点。
- **跨场次闭环**：弱点按固定主题聚合，记录首次/最近/次数/改善，按 1/3/7/14 天提醒复习。
- **有效回答不足时不给分**：少于 3 题只给逐题反馈，不硬凑四维评分。

#### 1.3.3 其他创新点

- 手机端先以 PWA 落地（可安装、离线壳、竖屏布局），不装 App 也能完成整场练习；
  原生 Android 客户端按「练习端三屏」推进，完整复盘留在电脑端，形成跨设备分工。

## 2 技术方案

### 2.1 总体架构

```
React + Vite（PWA）  ⇄  FastAPI（REST + WebSocket）  ⇄  SQLite（场次/事件/报告）
                                   │
                     Agent 运行时（单文件，32 个工具）
                       ├─ 技能：答辩评委 / 课程助教 / 模拟面试官
                       ├─ Workflow：逐题并行评分 → 汇总
                       └─ 模型：Anthropic 兼容端点（DeepSeek / Kimi 可切换）
                                   │
                     本地 faster-whisper（CPU，可选）
```

- 前端：React + TypeScript，Vite 构建；PWA 用 Service Worker 缓存静态资源，`/api` 与
  WebSocket 永不缓存；手机竖屏布局、安全区适配。
- 后端：FastAPI，WebSocket 推送增量文字与会话快照，断线重连后以服务端快照恢复。
- 存储：SQLite（快照 + 递增事件日志），每个场次独立，删除即彻底删除。
- 评分：Workflow 并行逐题评分，逐题流式回传，边评边显示。

### 2.2 功能详述

| 功能 | 说明 |
| --- | --- |
| 场次创建 | 场景（答辩/汇报/面试）、讲稿、轮数（10/15/20/30/50）、压力档位 |
| 讲稿导入 | `.docx/.pptx/.txt/.md`，服务端解析并转成段落标题；粘贴亦可 |
| 摘要卡 | 模型概括 + 规则兜底，逐条确认/改写/驳回 |
| 追问对话 | 一次一题、锚定陈述单元、题数硬上限、语音作答（可选） |
| 报告 | 四维评分、逐题证据与建议、单元覆盖、上一场检验点；Markdown/PDF 导出 |
| 成长画像 | 跨场次总分与四维趋势、岗位对比、反复短板、复习提醒 |
| 账号与隐私 | 评审/试用账号，Bearer 与 Cookie 双支持；记录可删除、可导出 |

### 2.3 关键技术

1. **单元切分与回链**：确定性规则切分，保留原文偏移；`text[start:end]` 恒等于单元文本，
   报告引用可逐字定位。超长讲稿合并相邻单元而不是丢弃。
2. **评分与证据**：逐题并行评分 → 证据校验（重试/标记）→ 代码计算维度均分与加权总分 →
   汇总报告引用同一组数字。场景不同维度不同（答辩 35/25/25/15）。
3. **实时性**：WebSocket 增量推送 + 事件驱动快照；请求去重、取消、断线恢复；
   报告逐题流式返回，首题约 30 秒可见。
4. **移动端**：PWA 安装、竖屏、离线壳；录音在本机，转写由服务端 faster-whisper 完成
   （CPU 下默认 small 模型，不用 GPU）。
5. **不可信输入防护**：上传文件做扩展名白名单、zip 解压体积与条目数上限、只读不落盘；
   候选人资料作为 JSON 数据处理，防止提示注入。

### 2.4 其他相关技术

- 依赖锁定与 CI（Ubuntu + Windows，Python 3.14）；前端 vitest + eslint。
- 备份/恢复脚本：数据库一致性快照与完整性校验。

## 3 项目计划

### 3.1 可行性分析

#### 3.1.1 技术可行性

- 追问、评分、证据校验、报告导出均已实现并通过自动化测试（后端 392 个测试函数 /
  收集 400 个用例，前端 12 个）。
- 模型通过 Anthropic 兼容端点调用，国内可直连；无 GPU 也能用 CPU 语音识别。
- 已有真实模型端到端验证：3–6 题的报告 23–52 秒完成。

#### 3.1.2 资源可行性

- 单台 2 核 2G 云服务器即可运行（文字 + CPU 语音；内存紧张时用 base 模型或关闭语音）。
- 无自建 GPU、无第三方付费语音服务；模型成本可按项目预算控制。

#### 3.1.3 市场可行性

- 目标用户明确：每年有答辩/课程汇报需求的本科生与研究生；练习是刚需但缺少反馈。
- 与题库式面试产品差异清晰：锚定个人讲稿、证据可回链、跨场次检验，而不是泛问题库。

## 4 总结与展望

作品已经完成从「讲稿输入」到「可回链报告」再到「下一场检验」的闭环，并在手机上可用。
下一步：完成真实用户两轮试用并用数据说明效果；完善 Android 原生客户端与 OPPO 软件商店上架；
扩展更多学科场景（开题、中期、竞赛路演）。
